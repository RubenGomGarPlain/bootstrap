## Architecture

### Architectural Style

**Decision:** Modular Monolith + VSA + CQS — single deployable unit with independently cohesive modules; vertical slices per feature; commands mutate state, queries read state. See ADR-0004, ADR-0006.

### Layers / Slices

| Layer | Responsibility | May Reference |
|-------|---------------|---------------|
| `Domain/` | Aggregates, entities, value objects, domain events | nothing (framework-free) |
| `Application/Features/<Entity>/` | Use-case handlers (MediatR), feature commands/queries/events | Domain, BuildingBlocks |
| `Infrastructure/` | EF Core DbContext, repositories, CAP bus setup | Application interfaces |
| `Api/` (Presentation) | Minimal API endpoints, module registration | Application only |
| `BuildingBlocks/` | `BaseEntity`, `ICommand`, `IQuery`, pipeline behaviours | nothing |
| `Contracts/` | Integration events shared across modules | nothing |

### Pattern Catalog

| Pattern | When to Use | Example |
|---------|-------------|---------|
| VSA (Vertical Slice) | Every new feature | `Application/Features/Todo/Commands/CreateTodo/` |
| CQS via MediatR | All use cases | `ICommand<TResult>`, `IQuery<TResult>` from BuildingBlocks |
| DDD Rich Entities | Domain logic with invariants | `Todo.CompleteTodo()` raises `TodoCompletedEvent` |
| Domain Events | State transitions inside aggregates | `Raise(new TodoCreatedEvent(Id))` |
| CAP + RabbitMQ | Cross-module async messaging | `TodoCreatedEventConsumer` in Notifications |
| EF Core | Commands and migrations | `TodoDbContext` |
| Dapper | Complex read queries, reporting | Direct SQL in query handlers |

### Dependency Rules

- `Domain` has zero external dependencies — no EF Core, no MediatR, no framework references
- `Notifications` MUST NOT import `Todos` internals — only `Contracts` integration events
- All cross-module communication goes through the message bus (DotNetCore.CAP + RabbitMQ)
- `BuildingBlocks` is a leaf — it MUST NOT reference any module
- `Contracts` is a leaf — it MUST NOT reference any module

### ADRs

- [ADR-0001](docs/adr/0001-record-architecture-decisions.md): Record architecture decisions
- [ADR-0002](docs/adr/0002-data-acces-startegy.md): Data access strategy (EF Core + Dapper hybrid)
- [ADR-0003](docs/adr/0003-aspire-as-base.md): Aspire as base technology
- [ADR-0004](docs/adr/0004-modular-monolith.md): Modular Monolith architecture
- [ADR-0005](docs/adr/0005-testing-strategy.md): Testing strategy (pyramid)
- [ADR-0006](docs/adr/0006-domain-driven-design.md): Domain-Driven Design
- [ADR-0007](docs/adr/0007-deferred-authentication.md): Deferred authentication strategy

### Compliance Rules

- New features MUST follow VSA: one folder per feature under `Application/Features/<Entity>/<Commands|Queries|Events>/`
- Cross-module references MUST go through `Contracts` events + message bus
- New architectural decisions MUST produce an ADR
- Domain layer MUST remain framework-free
- `BaseEntity`, `ICommand`, `IQuery` from BuildingBlocks MUST be used for all domain entities and CQRS contracts
- Architecture tests (`tests/ArchTests/`) guard dependency rules — violations are build failures

## Quality Assurance

### Test Strategy

**Pyramid:** Unit (many) → Functional (medium) → Arch (few, mandatory) → E2E (few, pre-merge)
**Philosophy:** Test behaviour, not implementation; domain logic is the highest-value test target

### Coverage

- Floor: 80% on Domain + Application layers
- Exclude: generated code, DTOs, EF migrations, configuration
- Enforcement: to be wired into CI gate (open: `Directory.Build.props` threshold)

### Test Types

| Type | Scope | When |
|------|-------|------|
| Unit | Domain entities, pure logic, handlers | Every PR |
| Functional | HTTP endpoints via `WebApplicationFactory` | Every PR |
| Architecture | Module dependency rules via ArchUnit.NET | Every PR — violations = build break |
| E2E | Full user flows via Playwright + Aspire | Pre-merge to main |

### Naming Convention

**Pattern:** `Should_<expected>_When_<scenario>`

### Testability Rules

- All handlers receive dependencies via constructor injection — no `new` for infrastructure
- Domain entities must be testable without EF Core or any framework
- Use Builder pattern for test data construction (see `tests/TodoUnitTests/`)

### Compliance Rules

- New public domain methods MUST have unit tests
- New endpoints MUST have functional tests
- Critical business logic MUST have >90% branch coverage
- Flaky tests MUST be quarantined within 24h
- ArchTests MUST remain green — never skip or ignore a dependency violation

## DevOps

### Pipeline Stages

| Stage | Trigger | Gate |
|-------|---------|------|
| Build + Unit Tests | Every push / PR | All tests green |
| Functional + Arch Tests | PR to main | All tests green |
| E2E Tests | Merge to main | All tests green |

## Security

### Known Gap: Authentication Deferred

> See ADR-0007. Authentication is explicitly deferred in v1. The following rules apply once auth is introduced.

### Threat Model (STRIDE — draft)

| Threat | Asset | Mitigation | Priority |
|--------|-------|-----------|----------|
| Spoofing | API endpoints | Auth (deferred — ADR-0007) | High (future) |
| Tampering | Todo state | Domain invariants + input validation | Medium |
| Information Disclosure | Todo data | Auth (deferred) + response shaping | High (future) |
| Denial of Service | API + RabbitMQ | Rate limiting + Aspire health checks | Low (future) |
| Elevation of Privilege | Module boundaries | ArchTests enforce module isolation | Medium |

### Authentication

**Strategy:** Deferred — see ADR-0007. When introduced, a new ADR must document provider, BFF vs token-based, and identity boundary ownership.

### Authorization

**Model:** Not defined. Will follow authentication ADR.

### Data Protection

- Input validation: `ArgumentException.ThrowIfNullOrWhiteSpace` at domain entry points
- No PII currently stored (demo data only)
- Secrets: `UserSecrets` for local; Key Vault references required for staging/production

### Supply Chain Security

- Central package management via `Directory.Packages.props` — prevents version drift
- `global.json` pins SDK version — ensures reproducible builds

### Compliance Rules

- All user input MUST be validated at the domain boundary
- Secrets MUST NEVER appear in logs or API responses
- When auth is introduced, all endpoints MUST require authentication unless explicitly marked public
- Critical CVEs in dependencies MUST be patched within 48h
- `Directory.Packages.props` MUST be the single source of package versions

## Cross-Validation Results

### Resolved Conflicts

| Conflict | Resolution | Rationale |
|----------|-----------|-----------|
| Security (no auth) vs QA (endpoint tests) | Document auth gap in ADR-0007; functional tests cover endpoint behaviour without auth for now | Demo/bootstrap intent is explicit; retrofit path is documented |

### Accepted Trade-offs

- No auth in v1 — intentional demo simplification; ADR-0007 makes it explicit and traceable
- No CI/CD pipeline yet — bootstrapping phase; GitHub Actions recommended when ready
- Hardcoded notification recipient (`hello@dotnet.com`) — known demo simplification; parameterize before production
